    Customer App Production Readiness Review¶

    Date: 2026-09-18
    Verdict: BLOCKED — not production-ready

    Accepted launch exceptions¶

    Per the product owner's instruction, this verdict does not count the following as findings:

    • OTP delivery is not implemented yet.
    • OTP is temporarily fixed to 123456.
    • API URLs still point to local development servers.

    Release blockers¶

    1. Failed checkout is reported as a successful order¶

    Severity: Blocker
    Evidence: apps/customer-app/src/services/api.ts:414, apps/customer-app/app/store/[id].tsx:356

    orderApi.createOrder catches every server or network failure and creates a local order with a fabricated order number and pickup code. The store screen then clears the cart and tells the customer that the order was sent to the vendor. This includes authentication failures, store closure, unavailable stock, server validation errors, and network failures. The vendor never receives the order.

    Remove the local success fallback. Keep the cart intact and surface the actual failure.

    2. Cached orders can leak between customer accounts¶

    Severity: Blocker
    Evidence: apps/customer-app/src/services/api.ts:339, apps/customer-app/src/services/api.ts:349, apps/customer-app/src/services/api.ts:216

    All customers share the customer_orders cache key, and logout clears only the token/device token. If customer A signs out, customer B signs in, and the order request fails, the app can display customer A's order history, notes, and pickup codes.

    Scope cached data to the authenticated customer and clear it during account changes. Prevent requests from a previous session from repopulating the cache.

    3. Empty and failed requests show fabricated customer data¶

    Severity: Blocker
    Evidence: apps/customer-app/app/(tabs)/orders.tsx:33, apps/customer-app/app/(tabs)/orders.tsx:175, apps/customer-app/app/(tabs)/index.tsx:57, apps/customer-app/app/(tabs)/profile.tsx:89

    A valid empty order list displays sample ready/completed orders. API failures display realistic fake stores and an Ahmed Khan profile. This hides outages and session failures and can direct customers to nonexistent stores or make them believe an order is ready.

    Render explicit empty, offline, and error states. Only use clearly labelled cached server data where the product requires offline reading.

    4. Variation pricing and cart lines are not preserved through checkout¶

    Severity: Blocker
    Evidence: apps/customer-app/app/store/[id].tsx:228, apps/customer-app/app/store/[id].tsx:306, apps/customer-app/src/services/api.ts:378, apps/backend/src/modules/orders/orders.service.ts:139

    The cart calculates option surcharges, but checkout sends selections only as free-text notes. The backend prices the base listing and cannot validate the selected options. The customer can therefore see one total and receive an order with another total. Cart entries are also keyed only by vendor-product ID, so adding the same product with different options merges the quantities and overwrites the earlier selection.

    Send stable variation/option identifiers, validate them and calculate their prices on the server, and key cart lines by the complete selection.

    5. Production can start with a public fallback JWT secret¶

    Severity: Blocker
    Evidence: apps/backend/src/modules/auth/auth.module.ts:24, apps/backend/src/modules/auth/strategies/jwt.strategy.ts:12

    JWT signing and verification use a source-visible fallback when JWT_SECRET is absent. A misconfigured deployment would accept forged tokens, including tokens claiming privileged roles.

    Require a strong configured secret and fail startup when it is missing.

    Major findings¶

    1. Expired sessions are not handled. apps/customer-app/app/(tabs)/_layout.tsx:44 swallows profile/auth failures, the entry screen trusts token presence, and API requests do not centrally handle 401. After token expiry the UI remains signed in and other fallback behavior can mask the failure.
    2. Push notification registration is absent. apps/customer-app/src/services/api.ts:238 and :464 define registration methods, but neither has a call site. No native notification permission/token acquisition package is installed. Foreground polling in AppHeader.tsx:35 cannot deliver ready/modification alerts while the app is backgrounded or closed, although push is in the V1 scope.
    3. Customer cancellation is absent. The app exposes only modification accept/reject at apps/customer-app/src/services/api.ts:440. It does not implement eligible order cancellation required by docs/business/08-functional-requirements.md:216.
    4. Cart state is screen-local. apps/customer-app/app/store/[id].tsx:50 loses the cart on navigation/restart and provides no cross-vendor clear-cart confirmation.
    5. Cart prices go stale. Product polling refreshes the catalog but does not reconcile products already in the cart. The app can continue showing an old price while the backend charges the current base listing price.
    6. Profile save failures are presented as success. apps/customer-app/app/(tabs)/profile.tsx:142 converts all server failures into “Profile updated locally,” but the value is only component state and disappears on reload.
    7. Order numbers have a finite collision-prone namespace. apps/backend/src/modules/orders/orders.service.ts:60 randomly selects one of 9,000 globally unique numbers without retrying collisions. Checkout failures become increasingly likely as order volume grows.
    8. Suspension/revocation is delayed until token expiry. apps/backend/src/modules/auth/strategies/jwt.strategy.ts:16 trusts the token's stored role without loading the current account status.
    9. Expo native dependencies are incompatible. bunx expo install --check reports expo-splash-screen@57.0.9 where SDK 52 expects ~0.29.24, and React Native 0.76.7 where 0.76.9 is expected.

    Documented V1 gaps¶

    • QR code generation/display for pickup is absent; the UI shows a QR icon and numeric pickup code only.
    • No customer test script or customer regression suite exists in the app package.
    • Several profile menu rows have no behavior, including notification preferences, dietary preferences, help, and terms/privacy.

    Automated customer test suite BLOCKED; no test script/suite is present
    Real push delivery BLOCKED; device registration is not wired

    The runtime screenshot used during review is stored at /tmp/customer-production-check.png and is intentionally not committed.

    Positive controls confirmed¶

    • Native auth tokens use Expo SecureStore.
    • Customer order reads are authenticated and filtered by customer ownership.
    • Base product price and current listing availability are validated server-side.
    • The installed iOS build launches and its principal discovery UI renders.

    Release decision¶

    Do not submit the customer app to production until all blockers are resolved and the major customer workflows are retested end to end on release builds. The accepted OTP and local-URL exceptions remain outside this decision as requested.
