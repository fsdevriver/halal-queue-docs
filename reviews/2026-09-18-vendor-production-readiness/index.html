    Review, vendor app production readiness, 2026-09-18¶

    Reviewed by: Separate GPT reviewer (gpt-5.6-sol), with main agent verification. Author editor: Antigravity; author model unknown, so model independence is not guaranteed. Scope: 30 application, backend, configuration, and native project files; current main plus uncommitted vendor-related work Verdict: Blocked

    Summary¶

    The vendor app is not production ready. Its production configuration cannot reach a deployed API, and multiple backend routes let one vendor read or mutate another vendor's orders and catalog listings. The pickup flow also bypasses the documented verification control. The installed iPad app reached login, API authentication and empty vendor order/catalog reads worked, and an iOS JavaScript export passed; full order behavior could not be exercised because the seeded vendor has no fixtures and its phone number cannot be entered in the app's ten-digit login field.

    Blockers¶

    🔴 Production builds target loopback development services, apps/vendor-app/src/services/api.ts:6¶

    Problem: Every API URL is derived from Expo's development host or a loopback/emulator address, and the OTA manifest URL points to http://127.0.0.1:3000 in apps/vendor-app/app.json:16. There is no production API or update URL configuration. Why it matters: A store-distributed build will call the iPad itself (or an unavailable development host), making login, orders, inventory, and updates unusable. The HTTP URLs would also expose credentials and order data if transport were relaxed. Suggested fix: Supply environment-specific HTTPS API and OTA origins during the build, fail the production build when either is absent or non-HTTPS, and generate the native update configuration from the same canonical source.

    🔴 Vendor roles can access and mutate other vendors' orders, apps/backend/src/modules/orders/orders.service.ts:284¶

    Problem: Status and modification authorization calculates ownership, but then accepts any account whose role is VENDOR or VENDOR_STAFF (isVendorRole at lines 288-290 and 564-566). The vendor queue endpoint trusts the caller-supplied vendorId without resolving it against the authenticated user (orders.controller.ts:54), and GET /orders is available to vendor owners because CASL grants them Manage Order. GET /orders/:id has no object-level authorization at all. Why it matters: A vendor can enumerate customer names and phone numbers from another store, alter another store's orders, or complete/cancel them. This directly violates the documented ownership isolation and BR-AUTH-103. Suggested fix: Resolve the actor's vendor membership server-side and require it to match order.vendorId for every vendor read/write. Restrict platform-wide listing to administrators, authorize single-order reads for the owning customer/vendor/admin, and remove role-only bypasses.

    🔴 Vendors can alter the global catalog and other vendors' listings, apps/backend/src/modules/catalog/catalog.controller.ts:93¶

    Problem: CASL grants vendor owners Manage Product, Category, QuantityType, and VendorProduct. Product routes therefore allow vendors to create/update/delete the administrator-owned global catalog. Vendor-product mutations accept arbitrary vendorId or listing IDs, while the service updates/deletes them without ownership checks (catalog.service.ts:233-277). Why it matters: One vendor can change global product definitions or another vendor's prices, availability, and listings. This conflicts with UC-014/UC-016 and FR-052/FR-053, which reserve the global catalog for administrators and limit vendors to their own listings. Suggested fix: Limit global catalog mutation abilities to administrators. Derive the vendor ID from the authenticated membership for listing creation and validate listing ownership for update, price change, and removal.

    🔴 Pickup completion bypasses pickup-code verification, apps/backend/src/modules/orders/orders.service.ts:297¶

    Problem: The backend explicitly completes PICKED_UP without validating dto.pickupCode, and the vendor UI sends PICKED_UP directly from both handover buttons without collecting a code (apps/vendor-app/app/(dashboard)/index.tsx:1372 and line 1721). Why it matters: Any tap, mistake, or unauthorized vendor request permanently completes an order without proof that the customer collected it. This contradicts UC-011 and FR-044 through FR-046. Suggested fix: Require the pickup code when the current status is READY_FOR_PICKUP, compare it securely to the order's code, reject invalid attempts, and make the UI collect/scan the code before completion.

    🔴 Public vendor routes disclose staff and owner contact details, apps/backend/src/vendors/vendors.controller.ts:39¶

    Problem: Both vendor list and detail routes are public, while their service responses include staff and owner IDs, names, email addresses, phone numbers, roles, business profiles, and operating records (vendors.service.ts:16-84). Why it matters: Unauthenticated callers can enumerate private employee and owner data across every vendor. This is a production privacy and abuse risk. Suggested fix: Create explicit public vendor response projections containing only storefront fields. Move staff, owner, and operational detail behind authenticated, role- and ownership-checked endpoints.

    Major¶

    🟠 Vendor staff cannot load their order queue, apps/backend/src/modules/orders/orders.controller.ts:55¶

    Problem: The queue route requires Manage Order, but VENDOR_STAFF receives only Read and Update in casl-ability.factory.ts:37-40. Why it matters: Staff can be validly assigned to a store yet receive a 403 when the app loads its primary order screen. Suggested fix: Require Read Order for the queue endpoint and pair that permission with the mandatory vendor-membership check.

    🟠 Session failures are replaced with a fake merchant profile, apps/vendor-app/app/(dashboard)/index.tsx:537¶

    Problem: Any /vendors/me error, including expired credentials, authorization failures, server errors, or malformed operating-hours JSON, is caught and replaced with a hard-coded Medina Meats profile. The login screen also accepts any authenticated role and immediately opens the dashboard (app/(auth)/login.tsx:48). Why it matters: The app presents a convincing but nonfunctional merchant session, hides outages and authorization problems, and can leave customer accounts inside a vendor interface. Suggested fix: Validate that login/profile roles are VENDOR or VENDOR_STAFF, clear invalid sessions, route authentication failures to login, and show an explicit retryable error for service failures.

    🟠 Access tokens expire without refresh or session recovery, apps/vendor-app/src/services/api.ts:74¶

    Problem: A refresh token is persisted, but request handling never uses it and treats 401 like any other error. The entry route considers the mere presence of an access token sufficient authentication (app/index.tsx:13). Why it matters: Long-running store terminals will silently stop polling and processing orders when the access token expires, and stale tokens keep routing users into a broken dashboard. Suggested fix: Implement single-flight refresh and one safe request retry, clear tokens and return to login when refresh fails, and validate the session during startup.

    🟠 Native order notifications are not implemented, apps/vendor-app/src/services/api.ts:222¶

    Problem: The client exposes device-token registration but never obtains or registers a token, does not depend on a notifications library, and only discovers orders by foreground polling. Its sound implementation uses browser AudioContext, so it produces no native alert. Why it matters: Backgrounded or locked store iPads will not alert staff to new orders, which can lead to missed orders and breached preparation expectations. Suggested fix: Add the supported Expo notification integration, request permission, register/revoke the native token with lifecycle handling, configure iOS/APNs entitlements, and handle foreground/background notification events and audible alerts.

    🟠 Expo dependencies are outside the SDK 52 compatibility set, apps/vendor-app/package.json:21¶

    Problem: The app declares Expo SDK 52 but installs expo-splash-screen 57.0.9, while Expo's dependency check expects approximately 0.29.24; it also reports React Native 0.76.6 where 0.76.9 is expected. The offline check exits unsuccessfully. Why it matters: A JavaScript export can succeed while native modules remain ABI-incompatible, causing build-time or device-only failures in splash/update behavior. Suggested fix: Align dependencies with the versions supported by Expo SDK 52 using Bun and rerun Expo's dependency check plus a native release build.

    Minor¶

    🟡 Order polling overlaps and suppresses ongoing failures, apps/vendor-app/app/(dashboard)/index.tsx:492¶

    Problem: A fixed three-second interval starts a new full-order fetch regardless of whether the prior one completed, keeps polling when the app is backgrounded, and silent polls swallow errors without visible stale-state indication. Why it matters: Slow networks can produce overlapping requests and out-of-order state updates; prolonged outages leave operators looking at stale data as if it were live. Suggested fix: Use a non-overlapping poll or subscription, pause with app lifecycle state, cancel stale requests, and surface connection/staleness status.

    🟡 The dashboard is a single 6,000+ line component, apps/vendor-app/app/(dashboard)/index.tsx:1¶

    Problem: Order polling, authorization-driven UI, store operations, inventory, notification state, modal workflows, and thousands of lines of styling are coupled in one component. Why it matters: Security-sensitive behavior is hard to review and changes are likely to create cross-feature regressions. Suggested fix: Split the screen by domain workflow and extract data hooks/services while preserving the current behavior and design.

    Strengths¶

    • Access and refresh tokens use SecureStore on native platforms rather than plain async storage.
    • Order state transitions are centralized in a backend transition map and updates/history writes use transactions.
    • Vendor listing reads compute availability consistently through the shared catalog service.

    Test coverage¶

    The vendor package has no test or lint scripts. Existing CI workflows call a different package manager and root scripts that are absent from the current root package. The Flutter workflow only echoes a message and watches old directory names. These do not establish a working Expo release gate. See .github/workflows/ci.yml, test.yml, lint.yml, and flutter.yml. This conflicts with the repository's Bun requirement and documented mobile testing strategy; no configuration was changed during this review.

    Vendor-app TypeScript typechecking passes, but there is no vendor test suite yet. Backend vendor tests exist, but the new order module is untracked and has no tests covering cross-vendor denial, pickup-code verification, staff access, or state transitions. Verification launched the installed iPad app to its login screen; an iOS JavaScript export completed (2,584 modules, Hermes bundle 4.76 MB), and direct API checks confirmed unauthenticated /vendors/me returns 401, seeded vendor login succeeds, /vendors/me resolves its vendor, and its own order/catalog endpoints return empty arrays. Seeded staff authentication also succeeds, but /vendors/me returns 404 for that fixture, so the staff workflow could not reach the queue. A native release build was not run. The seeded vendor phone (+1987654321) cannot pass the app's ten-local-digit input, and the seed has no orders/products, so login through the UI and business workflows remain unverified. Expo's dependency compatibility check exited 1 for the version mismatches noted above.
