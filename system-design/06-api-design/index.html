    API Design¶

    Purpose¶

    This document defines the API architecture, design principles, standards, and conventions for the Halal-Queue platform.

    The API serves as the communication layer between client applications and the backend while ensuring consistency, security, maintainability, and future extensibility.

    Design Goals¶

    The API shall provide:

    • Consistent request and response formats
    • Stateless communication
    • Secure authentication and authorization
    • Clear resource-oriented endpoints
    • Standardized error handling
    • Versioning support
    • Real-time updates
    • Backward compatibility

    API Architecture¶

    Version 1 uses:

    • REST APIs
    • JSON request and response bodies
    • HTTPS
    • JWT Authentication
    • WebSocket for real-time updates

    The backend exposes a single API consumed by:

    • Customer Mobile Application
    • Vendor Mobile Application
    • Admin Web Application

    API Versioning¶

    All endpoints shall be versioned.

    Example:

    /api/v1/

    Future breaking changes shall introduce a new major version.

    Example:

    /api/v2/

    API Style¶

    The API follows REST principles.

    Resources are represented by nouns rather than verbs.

    Examples:

    GET    /api/v1/orders

POST   /api/v1/orders

GET    /api/v1/orders/{orderId}

PATCH  /api/v1/orders/{orderId}

DELETE /api/v1/orders/{orderId}

    Avoid action-oriented endpoints such as:

    /createOrder

/updateVendor

/deleteProduct

    API Modules¶

    Endpoints are organized by business domain.

    Module Base Path
    Authentication /api/v1/auth
    Customers /api/v1/customers
    Vendors /api/v1/vendors
    Catalog /api/v1/catalog
    Cart /api/v1/cart
    Orders /api/v1/orders
    Pickup /api/v1/pickup
    Notifications /api/v1/notifications
    Admin /api/v1/admin
    Uploads /api/v1/uploads

    Authentication¶

    Version 1 supports:

    • Phone Number Registration
    • OTP Verification
    • Password Login
    • JWT Access Token
    • Refresh Token

    Authentication flow:

    Register

↓

Receive OTP

↓

Verify OTP

↓

Set Password

↓

Login

↓

Receive JWT Tokens

↓

Authenticated Requests

    Authorization¶

    Role-Based Access Control (RBAC) is used.

    Supported roles:

    • Customer
    • Vendor
    • Vendor Staff (Future)
    • Administrator

    Each endpoint defines the roles permitted to access it.

    HTTP Methods¶

    Method Purpose
    GET Retrieve resources
    POST Create resources
    PUT Replace resources
    PATCH Partial update
    DELETE Delete resources

    PATCH should be preferred over PUT for partial updates.

    Request Format¶

    Requests shall use JSON.

    Example:

    {
  "phoneNumber": "+12125551234",
  "password": "********"
}

    File uploads use multipart/form-data.

    Response Format¶

    All successful responses follow a standard format.

    Example:

    {
  "success": true,
  "message": "Order created successfully.",
  "data": {
    "orderId": "ORD-100001"
  }
}

    Pagination¶

    Collection endpoints shall support pagination.

    Example:

    GET /api/v1/orders?page=1&pageSize=20

    Response:

    {
  "success": true,
  "message": "Orders retrieved successfully.",
  "data": [],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 250,
    "totalPages": 13
  }
}

    Filtering¶

    Collection endpoints may support filtering.

    Example:

    GET /api/v1/catalog/products?categoryId=12

GET /api/v1/orders?status=READY

GET /api/v1/vendors?status=OPEN

    Searching¶

    Resources may support search.

    Example:

    GET /api/v1/catalog/products?search=rice

    Sorting¶

    Resources may support sorting.

    Examples:

    sort=name

sort=price

sort=-price

sort=createdAt

    HTTP Status Codes¶

    Status Meaning
    200 Success
    201 Created
    204 No Content
    400 Bad Request
    401 Unauthorized
    403 Forbidden
    404 Not Found
    409 Conflict
    422 Validation Error
    429 Too Many Requests
    500 Internal Server Error

    Error Response¶

    All errors follow a standard format.

    Example:

    {
  "success": false,
  "message": "Validation failed.",
  "errors": [
    {
      "field": "phoneNumber",
      "code": "INVALID_PHONE_NUMBER",
      "message": "Phone number is invalid."
    }
  ]
}

    Validation¶

    Requests shall be validated before business logic executes.

    Validation includes:

    • Required fields
    • Data types
    • Value ranges
    • Phone number format
    • String length
    • Business rules

    Invalid requests return HTTP 422.

    File Upload¶

    Image uploads use dedicated endpoints.

    Example:

    POST /api/v1/uploads/images

    Supported files:

    • Product images
    • Vendor logos
    • Business images
    • Profile images

    Uploaded files are stored in S3-compatible object storage.

    Real-Time Communication¶

    Real-time updates use WebSocket.

    Typical events include:

    • Order Created
    • Order Accepted
    • Order Ready
    • Pickup Completed
    • Notification Created

    WebSocket is used only for server-to-client events.

    Business operations continue to use REST APIs.

    Background Processing¶

    Long-running operations are processed asynchronously.

    Examples:

    • Push notification delivery
    • Scheduled jobs
    • Daily product availability reset
    • Retry processing

    Background jobs are queued using BullMQ and executed by the Worker application.

    Idempotency¶

    The following operations should be idempotent where applicable:

    • OTP resend
    • Refresh token
    • Retry background jobs

    Duplicate client requests should not create duplicate resources.

    Rate Limiting¶

    Sensitive endpoints should be rate limited.

    Examples:

    • Registration
    • OTP requests
    • Login
    • Password reset

    Rate limits protect against abuse and brute-force attacks.

    Security¶

    All API communication shall use HTTPS.

    Security measures include:

    • JWT Authentication
    • Refresh Tokens
    • RBAC
    • Input validation
    • Output sanitization
    • CORS
    • Rate limiting

    Sensitive information shall never be returned in API responses.

    API Documentation¶

    The OpenAPI specification is the authoritative API contract.

    Location:

    openapi/
└── openapi.yaml

    The specification defines:

    • Endpoints
    • Schemas
    • Request bodies
    • Responses
    • Authentication
    • Error responses

    Client SDKs and API documentation may be generated from this specification.

    API Evolution Policy¶

    The API follows backward compatibility principles.

    Allowed changes within the same major version:

    • Add new endpoints
    • Add optional request fields
    • Add optional response fields
    • Improve documentation

    Breaking changes require a new API version.

    Examples of breaking changes:

    • Removing endpoints
    • Removing response fields
    • Changing field data types
    • Changing authentication mechanisms

    Out of Scope¶

    This document does not define:

    • Individual endpoint specifications
    • Business workflows
    • Database schema
    • Internal module implementation
    • Client application logic

    These topics are documented separately.
