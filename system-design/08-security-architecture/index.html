    Security Architecture¶

    Purpose¶

    This document defines the security architecture for the Halal-Queue platform.

    It describes the authentication model, authorization model, data protection strategy, communication security, operational security controls, and business security rules used throughout the platform.

    The objective is to protect customer data, vendor data, business operations, and platform infrastructure while maintaining usability and scalability.

    Security Goals¶

    The platform shall provide:

    • Confidentiality
    • Integrity
    • Availability
    • Authentication
    • Authorization
    • Privacy
    • Auditability
    • Secure communications

    Security Principles¶

    The platform follows these principles:

    • Secure by Default
    • Least Privilege
    • Defense in Depth
    • Zero Trust
    • Fail Secure
    • Separation of Duties
    • Principle of Minimum Exposure

    Security controls shall be applied consistently across all applications.

    Authentication¶

    Version 1 supports:

    • Phone Number Registration
    • SMS OTP Verification
    • Password Authentication
    • JWT Access Tokens
    • Refresh Tokens

    Authentication flow:

    Register
      │
Receive OTP
      │
Verify OTP
      │
Set Password
      │
Login
      │
Receive Tokens

    Only verified phone numbers may create accounts.

    Authorization¶

    The platform uses Role-Based Access Control (RBAC).

    Supported roles:

    • Customer
    • Vendor
    • Administrator

    Every API endpoint explicitly defines the roles permitted to access it.

    Authorization is enforced by the backend for every request.

    Business Security Rules¶

    The platform enforces business-level authorization in addition to role checks.

    Examples include:

    • Customers may access only their own orders.
    • Customers may access only their own profile.
    • Vendors may manage only their own business.
    • Vendors may manage only their own branches.
    • Vendors may manage only their own product listings.
    • Vendors may access only orders belonging to their branches.
    • Vendors may verify pickup only for their own orders.
    • Administrators have platform-wide administrative access.
    • Pickup codes are single-use.
    • Completed orders cannot be modified.
    • Vendors cannot modify another vendor's information.

    Password Security¶

    Passwords shall:

    • Never be stored in plain text.
    • Be hashed using Argon2id.
    • Never be returned by APIs.
    • Never be logged.
    • Never be reversible.

    Password complexity requirements are enforced during registration and password changes.

    JWT Security¶

    Authentication uses:

    • Short-lived Access Tokens
    • Long-lived Refresh Tokens

    Access Tokens:

    • Used for API authorization.
    • Sent in the Authorization: Bearer header.
    • Contain only required claims.

    Refresh Tokens:

    • Stored securely.
    • Rotated after successful refresh.
    • Revocable.
    • Invalidated during logout.

    Session Management¶

    The backend uses stateless authentication.

    Session information is represented by JWTs.

    Refresh token metadata may be stored to support:

    • Logout
    • Token revocation
    • Device management (future)

    Expired sessions require re-authentication.

    OTP Security¶

    OTP verification includes:

    • Expiration time
    • Maximum verification attempts
    • Maximum resend attempts
    • Single-use validation

    OTP values:

    • Are never stored in plain text.
    • Are invalid after successful verification.
    • Cannot be reused.

    API Security¶

    All APIs require:

    • HTTPS
    • JWT Authentication
    • Input Validation
    • Output Sanitization
    • Rate Limiting
    • CORS Protection

    Business validation occurs after authentication and authorization.

    WebSocket Security¶

    WebSocket connections require authentication.

    Security requirements include:

    • JWT authentication during connection
    • Authorization before subscribing to private events
    • Connection termination after token expiration
    • Access limited to authorized resources

    Typical events include:

    • Order updates
    • Pickup updates
    • Notifications

    Data Protection¶

    Sensitive information includes:

    • Phone numbers
    • Password hashes
    • Refresh tokens
    • OTP verification data

    Sensitive information shall:

    • Never appear in logs.
    • Never appear in error responses.
    • Be encrypted where appropriate.
    • Be accessible only to authorized users.

    File Upload Security¶

    Uploaded files shall be validated before storage.

    Validation includes:

    • File type
    • MIME type
    • File size
    • Extension
    • Virus scanning (future)

    Allowed uploads include:

    • Product images
    • Vendor logos
    • Business images
    • Profile images

    Executable files are prohibited.

    Files are stored in S3-compatible object storage.

    Rate Limiting¶

    Rate limiting protects public-facing endpoints.

    Examples include:

    • Registration
    • OTP requests
    • OTP verification
    • Login
    • Password reset
    • Public catalog requests

    Limits shall be configurable.

    Audit Logging¶

    Security-related events shall be logged.

    Examples include:

    • Registration
    • Login
    • Logout
    • Password changes
    • OTP verification
    • Failed authentication
    • Failed authorization
    • Vendor approval
    • Administrative actions

    Audit logs shall never contain:

    • Passwords
    • OTP values
    • JWT tokens
    • Refresh tokens

    Security Headers¶

    Responses should include appropriate security headers.

    Examples:

    • Strict-Transport-Security (HSTS)
    • X-Content-Type-Options
    • X-Frame-Options
    • Referrer-Policy
    • Content-Security-Policy (Admin Web)

    Cross-Origin Resource Sharing (CORS)¶

    Only approved client applications may access the API.

    Production origins shall be explicitly configured.

    Credentials shall never be accepted from untrusted origins.

    Secrets Management¶

    Sensitive configuration includes:

    • JWT signing keys
    • Database credentials
    • Redis credentials
    • Object storage credentials
    • Firebase credentials
    • SMS provider credentials

    Secrets shall:

    • Never be committed to source control.
    • Be stored using environment variables or a secrets manager.
    • Be rotated periodically.

    Dependency Security¶

    Third-party dependencies shall be:

    • Regularly updated
    • Vulnerability scanned
    • Reviewed before adoption
    • Removed when no longer maintained

    Infrastructure Security¶

    Production infrastructure shall provide:

    • HTTPS termination
    • Firewall protection
    • Private database network
    • Private Redis instance
    • Restricted object storage access
    • Encrypted backups
    • Monitoring and alerting

    Incident Response¶

    The platform shall support:

    • Security event detection
    • Audit log investigation
    • Token revocation
    • Credential rotation
    • Recovery procedures
    • Post-incident analysis

    Future Enhancements¶

    Future versions may introduce:

    • Multi-Factor Authentication (MFA)
    • Passkeys (WebAuthn)
    • Device management
    • Biometric authentication
    • Single Sign-On (SSO)
    • Hardware security keys
    • Fine-grained permissions beyond RBAC

    Out of Scope¶

    This document does not define:

    • NestJS implementation details
    • Cloud infrastructure configuration
    • CI/CD security pipelines
    • Operating system hardening
    • Network topology

    These topics are covered by implementation and deployment documentation.
